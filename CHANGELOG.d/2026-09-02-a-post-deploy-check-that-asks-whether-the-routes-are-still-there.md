date: 2026-09-02
title: "A post-deploy check that asks the running site whether its routes are still there — the one question no other gate can ask"
---

`npm run check:live-routes` asks a RUNNING site, anonymously, about every route in `scripts/route-table.json`. It was written after doing exactly that by hand twice on 2026-09-02 — four routes after `94773e3`, twenty-eight after `fd438a6` — because OA-231 had moved 24 routes between files and **nothing in any of the three repositories could see a lost one**: `/health?deep=1` asks whether the process came up, the byte gates ask whether the drawn output still matches, `npm test` asks the laptop's build. A route that stops being registered does not throw. It 404s, quietly, to whoever asks for it next.

- **The population comes from something other than the app under test.** `route-table.json` is the snapshot recorded from the unsplit server and owned by `test-admin-plugin.mjs`. A route this app no longer registers is precisely what is being looked for, so the list cannot come from the app.
- **Two different things return 404 and they are told apart by the BODY, measured rather than assumed.** `{"message":"Route GET:/x not found","error":"Not Found","statusCode":404}` is the router saying the route is GONE; `{"ok":false,"error":"No published map with that name."}` is the app answering correctly about a slug nobody published, which is what `/m/:slug` must do. So the universal rule — *no route may produce a router 404* — needs no policy per route at all.
- **It catches the opposite fault too.** A guarded route that answers **2xx** to a stranger is a route that is still there and a guard that is not, and a check asking only "is it there" is the one that ships an open door.
- **A route it has no rule for exits 2 and is named**, never skipped. That is what stops the check quietly shrinking as routes are added, and it is this repository's oldest convention: a check that cannot find its subject must not report clear.
- **Safe against production, and that was established by measurement.** Guarded routes refuse before doing anything; the six a stranger may legitimately POST to are sent an empty body and each was confirmed to answer 4xx and create nothing (`/api/apply` and `/api/contact` 400 on their fields, `/api/auth/request` 400 on the address and emailing nobody, `/api/public/feedback` 404 on the map, `POST /auth/verify` 403 from the CSRF hook, `POST /api/auth/logout` 200 having logged nobody out).
- **Real identifiers where the site can supply them.** It reads `/api/public/maps` first, so `/m/:slug` is asked about a town that exists and must serve 200 rather than merely not-404. Where nothing is published — a fresh instance, or the scratch server the harness drives — it says so in the run and falls back to the router rule only, because a weaker check reported as a strong one is worse than a weak one. **Its first run found a bug in itself**: `:slug` means an ORGANISATION under `/o/` and `/api/public/orgs/` and a MAP everywhere else, and filling both from the map list made two correct routes look broken.
- **`prove-red-live-routes.mjs` is unlike the other harnesses here** — the checker asserts nothing about the source, so the only way to break its subject is to start a real server from a mutated copy and point it at that. Four arms: a route deleted, a guard deleted, a page redirect deleted, and a rule removed from the checker itself (which must exit 2, not 1). All four caught for their own reason, control green. It asks the OS for a **free port** rather than writing one down, which is the same lesson `CBM_NO_LISTEN` already carries.

Live result on `fd438a6`: **93 routes — 19 public, 56 guarded, 9 page, 9 reaches — all answering.** `npm test` 51 run, 0 failed, 2 excluded.
