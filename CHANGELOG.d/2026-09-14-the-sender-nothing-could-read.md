date: 2026-09-14
title: "The sender nothing could read"
---

- **`/health?deep=1` now reports the configured sender.** `configStatus()` named the email provider and whether its key was present, and said nothing about `EMAIL_FROM` — the one piece of email configuration that decides what a stranger sees in their inbox. It lives only on the host: no repository holds it, no probe returned it, and the only way to learn it was to send yourself an email and look. `checks.email` now carries `from` verbatim, in every branch including the fault branches, because a fault branch is exactly when an operator is reading this object and a field present only when things are fine is a field missing when it is wanted. It reaches only a caller holding `METRICS_TOKEN` or a signed-in admin, which is where `checks{}` has been gated since 2026-08-20; `RESEND_API_KEY` stays out of every surface, and a From header is on every email that leaves anyway.

- **It cost something real, which is why it is a field and not a note.** On 14 September a session ran the pre-send check that `Correspondence/CORR-001` message 009 demands of itself — a letter to the member of the public who reported the Ramsey faults, telling him he now has a seat to look at drafts. The letter said the sign-in email would come from *Peter Cooper - BusMaps.uk*. With nowhere to read the live value, the session inferred it from this repository's own deploy entry for `8493db1`, which says `EMAIL_FROM` is a bare address and **recommends** setting `Name <address>`, found nothing recording that it had been done, and rewrote a true sentence into a weaker one naming only the address. Peter had set it on 12 September, the day that entry recommended it. A document arguing for a change is the best evidence there is that the change may since have been made.

- **The sender is reported and deliberately not graded.** A bare address is a poorer sender, not a broken one, and `ok:false` here drives a 503 on `/health?deep=1` and pages an operator. The obvious next edit — warn when there is no display name — would turn a cosmetic property into an outage alert, so `scripts/test-audit-p1.mjs` carries a control asserting that a bare `EMAIL_FROM` stays healthy and is still reported as it stands.

- **One place owns the default.** `emailFrom()` in `src/config.js` takes an optional `env` so `configStatus()`, which is driven by an injected environment in its tests, asks the same function rather than spelling `'BusMaps.uk <noreply@busmaps.uk>'` a second time. A probe reporting a default that no email has ever carried would be worse than a probe reporting nothing.

- **Six new assertions, and three of them were watched go red.** Dropping `from` from the unknown-provider branch fails *…and on a fault branch*; spelling the default a second time one hyphen differently fails *unset falls back to the same default `emailFrom()` uses*; and grading a bare address as a fault fails *a bare address is still healthy*. 86 tests, 0 failed.

- **One thing this does not fix.** The deploy entry for `8493db1` in `docs/DEPLOY.md` still reads as though `EMAIL_FROM` were unset, and it is the sentence that caused the error above. It is not corrected here because a branch already open on that file appends to the same line, and a conflict on a 400 kB line is worth more than the tidy. The fact is recorded here in the meantime.
