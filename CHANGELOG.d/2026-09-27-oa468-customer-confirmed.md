title: "A managed customer's emailed yes is recorded as the publish-review evidence"
---

- **Publishing a managed customer's map records their emailed yes (buses-data OA-468).** The portal sends a managed customer nothing (#402), so they agree to a version by answering Peter's email, and until now the publish decision had nowhere to say so. On a managed customer's map the review screen now asks for the date they confirmed and the correspondence message that holds it (`CORR-nnn/nnn`), and holds **Publish** until both are filled. `POST /api/review/:id/approve` refuses a managed map without them (`400`, `code: customer-confirmation`) and stores `customerConfirmed: { by: 'email', on, ref }` in the decision evidence and the audit row; the decided view shows it. On any other map the fields do not appear, and a confirmation sent anyway is validated rather than stored malformed. `GET /api/review/:id` gains `request.managed`. The validator is `validateCustomerConfirmation()` in `src/publish/index.js`. [R3 Step 3](docs/R3-review-and-publish.md#step-3--complete-the-review-checklist) says what the approver does.
- **`scripts/accept-publish-batch.mjs` takes `--confirmed "<map id>:<YYYY-MM-DD>:<CORR-nnn/nnn>"`**, once per managed map, checked with the same validator before anything else runs, so a typo exits 2 instead of failing half-way through a run that has already accepted and submitted the map. A dry run prints what it would record.
- **New `scripts/test-customer-confirmation.mjs` (`npm run test:customer-confirmation`)** pins the validator's edges, the route's refusal and record, the free-customer path, the screen and the batch flag. With the managed requirement removed from the route, six of its checks go red.
- **Deploy history, written before the deploy per [DEPLOY §3b](docs/DEPLOY.md#3b-the-deploy-history-entry-is-written-before-the-deploy-and-merged-with-it).** This pull request's merge is the commit that goes live. It changes a route and the review screen, and no schema: the evidence column already holds JSON. The new fields appear only on a map whose customer's Plan on the admin Customers screen reads `managed`. The §4 read-back is `X-App-Version` naming the merge and `/health?deep=1` answering 200.
