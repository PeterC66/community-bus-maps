date: 2026-08-25
title: "The audit's P1 block: bearer tokens out of the clear, personal data with an end date"
---

`Development Docs/technical-audit_2026-08-25.md` in `buses-data`, findings N3, N7, N8 and N15. (N11 and the gate-board half landed in `claude-skills`; N4 closed earlier the same day; N16 is six S6 runs and has not been started.)

- **`session` and `magic_link` hold the token's SHA-256, and nobody was signed out.** Both tables held working bearer credentials in clear text — a live cookie for every signed-in user, and a working sign-in link for fifteen minutes — and `scripts/backup.mjs` copies the database unencrypted to a laptop where the copies were kept indefinitely. The code already *knew*: `sessionHandle()` exists precisely so the admin console never displays a token, with a comment explaining that a list of them is a list of accounts anyone holding it can become. The reasoning stopped one hop short of the store. Every accessor now takes the raw token and hashes it internally, so no caller can forget and no path can write a raw one by accident; the migration hashes what is already there, computed from the values it replaces, so **existing cookies keep working**. The displayed handle is unchanged — it was always a prefix of exactly this hash.
- **The column is still called `token`, deliberately, and the reason is the rollback.** `docs/DEPLOY.md` promises a rollback to the previous release and rests it on "the older code's `SELECT *` tolerates an unknown column". A rename does not leave an unknown column, it leaves a *missing* one, and the previous release's `WHERE s.token = ?` would throw on every request to `/api/`, `/app`, `/auth/` and `/metrics` — a total outage at the exact moment you are rolling back. Leaving the name alone degrades gently instead: old code compares a raw cookie to a hash, matches nothing, everyone signs in again. Every `SELECT` aliases it to `token_hash`, so no JavaScript holds a field called `token` that is not one.
- **The migration crashed on boot, and only a real server found it.** `hashStoredTokens()` is called from the migration IIFE while `const LOOKS_HASHED` sat below it — a temporal dead zone. Every assertion passed, because they all call the function *after* module load and because a test database is empty, and `[].filter(fn)` never calls `fn`. Green suite, dead production: the app threw `Cannot access 'LOOKS_HASHED' before initialization` the first time it started against a database with a session row in it. There is now a test that loads the module in a **child process** against a seeded database file, which is the only way to test a load path, and it was watched go red on the restored bug.
- **`scripts/accept-publish-batch.mjs --mint` was rewired in the same change.** It writes a session row directly over ssh; inserting the raw token would have produced a row the server could never match, so the mint would report success and the first API call would 401 with nothing to explain it. Both the mint and the revoke now hash.
- **Backups are encrypted before they leave the box.** `BACKUP_RECIPIENT` takes an **age public key** and the database copy is written as `portal.sqlite.age`; the private key lives in a password manager and never touches the VPS, which is the point of an asymmetric key here — a passphrase would have to sit on the box it is protecting against. Only the database is encrypted: `maps/` is published material anyone can fetch, and encrypting it would make the restore drill harder at the worst possible moment. Unset means plaintext and **says so on every run**, because a box that stops taking backups over a missing key is worse off than one taking readable ones. `age` exiting 0 having written nothing is checked for explicitly — the plaintext copy is only deleted after the encrypted one is read back. Proved both ways, including a round trip: the ciphertext is refused by SQLite as "file is not a database", and decrypts to an 11-table database that opens.
- **The laptop mirror has a retention limit** (`pull-backups.ps1`, 90 days) with a floor of the newest 7 snapshots however old they are — because if the host's cron dies for four months, an age-only rule would quietly empty the mirror at exactly the moment it is the only copy left. Pruning runs **only after** the freshness assertion passes: pruning on a failed pull is how a backup system becomes a deletion system.
- **Personal data has an end date.** Nothing had ever deleted a row from `application` or `message` — names, emails, phone numbers and free text from public forms — so the privacy statement's "we keep it while your organisation uses the service" described an intention, not a mechanism. Now: **24 months**, purged daily by the running server, with applications belonging to a **live customer exempt** for as long as the account exists, since that row is the record of how the account came about and the evidence behind the vetting decision. The exemption ends with the account, which the tests assert in both directions.
- **An erasure request has a script and a runbook.** `scripts/personal-data.mjs --show / --erase / --retention`, dry run by default, matching addresses case-insensitively because people apply under one spelling and write in under another. It deliberately does **not** touch `user`: deleting that row orphans the audit trail of who published which map. `docs/DEPLOY.md` §5b covers the account separately, and covers the step that is easy to skip — an erasure that stops at the live database is not one, because a restore brings the person back, so the runbook says to record the date the last backup holding them rotates out.
- **The privacy statement is out of draft** and names a data controller for the first time. It had read "Working draft — to be confirmed before the service opens publicly" since 25 July while the apply form was already collecting names, emails and phone numbers.
- **CSRF is a double-submit token enforced at one choke point.** `SameSite=Lax` was the entire defence: a browser default that has been softened before, absent on older browsers, and no help at all against login-CSRF via a top-level GET. The guard is a single hook over every mutating method with its two exemptions stated as **properties** of the request — no session cookie (nothing to abuse), or an `Authorization` header (never sent automatically) — rather than as a list of routes, because a list is right on the day it is written and wrong about the eighty-sixth route. On the client, `public/js/csrf.js` patches `window.fetch` once instead of editing twenty-six call sites in ten files, so there is no caller left to forget.
- **Sign-in cannot be fired from another site, and webmail still works in one extra click.** The attack is real: an attacker requests a link for their *own* account and makes the victim's browser follow it, silently signing the victim in as the attacker where everything they do next is visible. The obvious fix breaks the product — a link clicked in Gmail arrives with `Sec-Fetch-Site: cross-site`, indistinguishable from the attack, so refusing it would mean sign-in worked from desktop mail clients and nowhere else. Instead a user-initiated arrival signs in exactly as before, and a cross-site one gets a confirmation page **on our origin** naming the account, whose button posts back with a token an attacker's page cannot read. The GET never consumes the link — `peekMagicLink` exists for that — or anyone could destroy a real user's sign-in link by making their browser fetch it once. Driven end to end in a browser across a genuine cross-origin navigation.
- **The README no longer claims a control that has never operated.** Separation of duties is enforced in code and overridden on this deployment, because there is one operator: every publication to date is stamped `selfApproved: true`. The sentence is now conditional, and "a second person holds `approver`" is item 1 of a new **pre-customer checklist** (`docs/H1-operations-handbook.md` §3b) rather than a backlog row — it is the only entry there that no amount of work closes.
- **`npm test` is 15 suites.** `scripts/test-audit-2026-08-25.mjs` asserts all of the above through the database and over real HTTP rather than by reading the source, and six deliberate one-line breaks were each watched redden the assertion that names them.
