---
date: 2026-08-31
title: "The vendored engine learns which points of interest matter, and stops deciding it by name length"
---

Three engine files re-vendored — `poi_select.js`, `place/gen_internal.js` and `label_placer.js` — plus a refresh of the committed area fixture. The skill-side change is OA-202 and OA-066 in `buses-data`; what reaches this repository is the code the portal runs when it redraws a sheet, so it has to arrive here or the live engine keeps deciding what a crowded map says by counting characters.

- **The finding the change came from.** 98% of every dropped label across the whole estate is a point of interest, and 100% of the numbered place index is. `labeller.js` sorts on priority, then the LONGEST text, then insertion order — and until today every POI, stop name and road name entered at priority 0. So when a sheet ran out of room the survivor was decided by how many characters its name happened to have. That is a sound way to pack a page and it is not a statement of value.
- **`poi.tiers`, a per-map key: `"<category>:<name>"` → `must` / `may` / `miss`, or `{tier, as}` to rename.** `may` is the default and is exactly today's behaviour, which is what lets this ship without moving a byte on any map that has not been classified — all 20 gate PASS unchanged. `must` prints the name whatever the category and enters at `priority: 10, mustPlace: true`. `miss` is dropped at **selection**, before anything reserves page area.
- **`miss` is deliberately NOT this app's `internal.pois[...] = {hide: true}`.** The safe-subset hide is a render-time override applied after the map is built, gated, published and rendered — so `ci-reference`, the byte gate and the quality ledger all go on describing a sheet nobody sees. A `miss` never reserves its 4.2 mm box, never becomes a placer anchor and never appears in any of the three. Same visible outcome, opposite provenance.
- **`mustPlace` has no veto, so the build says when it failed.** Relaxing the hard grid cannot invent space, and a candidate box outside the frame is refused either way. Any `must` the placer still dropped is named on `stderr`, as is any `tiers` key that matched no POI on the sheet. A customer answer that failed in silence is worse than one nobody asked for.
- **`label_placer.js` teaches the v1 placer the same flag.** No map in the estate selects `labels.engine: "v1"`, so this moves nothing and is certified by nothing but its own two assertions — which is the reason to write it. Without it, one `routes.json` key would have meant *force this label* on seventeen maps and *drop it silently* on any map that happened to choose the other placer.
- **What it did on the one map it has been applied to.** High Wycombe's three internal sheets: 12 labels gained, 12 hard collisions lost, 11 dropped labels recovered. The lever was 26 industrial estates that draw a symbol the auto-name set can never label coming off the frame — fewer INPUTS, not a cleverer placer. It also stops that town's diagram printing `Bellfield House Communicty Centre`, OpenStreetMap's spelling, which a `tiers` `as` corrects.
- **The area fixture moved with the vendoring, in the same commit.** `Areas/_portal-fixture/St Ives` now holds v6.66. A fixture frozen alongside an engine change passes its own gate by construction and proves nothing; `verify:area`, `verify:defaults` and `verify:place` were all re-run against the refreshed one and all PASS.
- **One town is deliberately not on the new engine.** Wisbech was delivered as proposed update #139 half an hour before this change landed and the customer has been emailed. Rebuilding it would supersede the version they are being asked to accept, and re-delivering to correct that would put a second notice in the same inbox inside the hour. It carries a dated, hash-keyed exception in `status.js` that expires by itself the moment Wisbech is next built.
