title: "propose-update can say what it would stage first"
---

- **`scripts/propose-update.mjs` takes `--dry-run` (buses-data OA-228).** It supersedes any pending proposed update, inserts a `proposed_update` row, stages the payload under the map's pack, stores the diff and emails the customer, with no way to see any of it first — and before this change `--dry-run` was silently ignored, so a run meant as a look did all five, the email included. It now reads `confirm('remote')` from `scripts/lib/cli.mjs`: the default is unchanged, and `--dry-run` runs every refusal the real run makes — the map, its built data, `--src`, the payload's shape, the live `routes.json` — then names the pending update it would supersede, the files it would stage, the service-facts and landmarks diff (against `--src`) and whether the customer would be emailed, and writes no row, no file and sends nothing. The staging filter is one function both paths share, and the diff print-out one function both paths call. New `scripts/test-propose-update.mjs` (`npm run test:propose-update`) counts the rows of every table and lists every file in a throwaway store before and after, checks that no notification is attempted, that two refusals still refuse under `--dry-run`, and uses a real run as the control; against the old script it fails 12 of its 21 checks. [R4](docs/R4-update-cycle.md) and [H1](docs/H1-operations-handbook.md) name the flag. The seventh of the nine scripts OA-228 lists; one pull request each.
- **Deploy history, written before the deploy per [DEPLOY §3b](docs/DEPLOY.md#3b-the-deploy-history-entry-is-written-before-the-deploy-and-merged-with-it).** This pull request's merge is the commit that goes live. The server does not import `propose-update.mjs`, so nothing a visitor or a customer sees changes: no schema, route, UI or engine change.
