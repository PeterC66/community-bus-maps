date: 2026-09-02
title: "npm test discovers its tests, and four of them had drifted out of the chain"
---

- **`npm test` was a 36-command `&&` chain in `package.json` and is now [`scripts/run-tests.mjs`](scripts/run-tests.mjs)** (buses-data OA-224, Tier 2.2). The chain had three faults and the runner exists to remove all three. It **stopped at the first failure**, so one red test hid every test after it — you fixed one thing, re-ran, and found the next. Nothing **tied it to the files on disk**: of the 37 `test-*`/`prove-red-*` files in `scripts/`, **four were absent from it**, and the only way to discover that was to diff the chain against `ls`. And it **named each invocation a second time**, so an entry that forgot `--env-file-if-exists=.env` would have run a different command under the same name and reported it under the right one.
- **The runner globs the files and takes each one's command from the `package.json` script that owns it**, so `npm run test:svg` and the runner cannot diverge. A test that lands is in the suite that day. It prints a verdict and a duration per file and a summary at the end, and exits 1 if any failed — 0 ok, 1 a test failed, 2 the runner was used wrongly.
- **Two of the four strays were run, and two are excluded with a reason that says where they DO run.** `prove-red-fixture-drift.mjs` and `prove-red-engine-source.mjs` need nothing but the filesystem and are now in `npm test`; `test-engine-selfsufficient.mjs` and `prove-red-selfsufficient.mjs` need `BUSES_DIR` and stay in `verify.yml`. **An exclusion is not a hole**: the runner exits 2 on one with no reason, and on one naming a file that is no longer there, because a stale exclusion hides nothing and reads as coverage. The exclusions print on every run rather than living silently in a file.
- **Three test files had no npm script of their own** (`test-audit-2026-08-25`, `test-backup-retention`, `test-change-summary`) and now do; the runner names any file that does not, in case that was an oversight.
- **Falsified before being trusted, and watched go red on the fault it was written for.** [`scripts/prove-red-run-tests.mjs`](scripts/prove-red-run-tests.mjs) drives six cases plus two controls over scratch repositories under the temp dir (~3 s, no database, no fixture repository), and runs FIRST in `test.yml`: a bug in the thing that decides whether the suite is green does not make one test wrong, it makes the whole verdict wrong in the reassuring direction. The case that carries the most is the flag one — the scratch test passes only if the `.env` that `--env-file-if-exists` loads reached it, with a control proving the flag came from the npm script and not from the ambient environment. Reinstating the chain's stop-at-first-failure in the runner turns **exactly one** assertion red: *a test AFTER the failure still ran*.
- **`npm test` is green throughout** — 39 run, 0 failed, 2 excluded, 87 s.
- **New: [`docs/CONVENTIONS.md`](docs/CONVENTIONS.md)** (OA-224, Tier 2.4). One sheet settling flag names, exit codes (including the `3` that two scripts already use for "the input is not the shape it claims to be"), which stream carries what, the `--apply` for local mutators versus `--dry-run`/`--yes` for anything touching the VPS, the naming rule and the Node pin. It describes what is already true and **names the one divergence rather than fixing it here**: `engines` says `>=22` while the Dockerfile and all four workflows are on 24. Linked from `CLAUDE.md` and `docs/DEVELOPING.md`. Adoption is item by item in Tier 3, not on sight.
- **`docs/DEVELOPING.md` gains a section on the runner and loses a dead test name** — it told you to re-run `scripts/test-svg-sanitise.mjs`, which has never existed in this repository; the sanitiser's fixture corpus is `scripts/test-inline-svg.mjs` (`npm run test:svg`).
