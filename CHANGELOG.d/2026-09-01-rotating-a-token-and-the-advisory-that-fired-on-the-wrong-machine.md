---
date: 2026-09-01
title: "Rotating a token, and the advisory that fired on the wrong machine"
---

`METRICS_TOKEN` leaked into a Claude transcript for the second time in ten days and had to be rotated. The rotation itself was five commands; what came out of it was that neither the leak nor the rotation had anywhere to live.

- **The two leaks share a variable and nothing else.** On 2026-08-22 a `sed` tried to redact `printenv` output and the pattern was wrong. The rule written afterwards — ask a question whose *answer* is not the secret, fingerprint rather than print — is sound, and it did not help on 2026-09-01, because the second leak was `grep -rn "METRICS_TOKEN"` over the repository root while working out where the variable is configured. `.gitignore` governs **git**, not the filesystem, so `.env` line 40 came back in full. Nothing selected the secret for printing and no redaction was attempted, so every instinct the first rule trains was satisfied. The exposure came from the search's **scope**, which is fixed before you know what is in range — and a `.env` is precisely the file that answers *"where is this configured?"*, so the better the question, the more certainly the grep finds the value. The remedy is a path, not a filter: name the subdirectories, `--exclude=".env*"`, or `git grep`, which sees only tracked files and structurally cannot reach an ignored one.
- **`scripts/rotate-secret.mjs`, and the three things it refuses to do by hand.** It generates host-side (`openssl rand -hex 24` written by a `printf` **builtin**, so the value is never an argument in `ps`, never echoed, never in shell history at either end, and never returns to the laptop — the script installs a value it does not itself see). It verifies by comparing the `.env` fingerprint against the **running process**, because a config read cannot tell you a container was recreated, and it uses `up -d` rather than `restart`, which does not re-evaluate the `${VAR}` substitution. And it **exercises the old value** afterwards: a credential is not revoked because a file changed, it is revoked when using it fails. `METRICS_TOKEN` loses `gitSha` from `/health?deep=1`; `OPERATOR_TOKEN` gets a 401. `STATUS_TOKEN` opens only a POST that writes the status snapshot, so it has no safe read-only probe and its revocation is reported **UNPROVED** rather than implied — the whole point being to not launder a config read into a claim about the world.
- **It keeps no `.env` backup, which is the opposite of the obvious.** `cp .env .env.bak-$(date)` leaves a cleartext duplicate of every *other* live secret beside the original for ever. Two such files were on this host: one written by the by-hand rotation an hour earlier, and one five weeks old holding a live `RESEND_API_KEY` and `STATUS_TOKEN`. Compared key by key against the live file by fingerprint, the old one held **no key the live file lacked** and differed in exactly one value — the token being retired. The only thing such a backup preserves is the thing you are deliberately throwing away, so the old fingerprint is printed and the file is left alone.
- **The deploy advisory was asking the wrong machine, and only became visible when the answer changed.** `deploy.mjs` step 5 warned *"no METRICS_TOKEN in this shell"* off `process.env.METRICS_TOKEN` — the laptop — while the token that step actually authenticates with is sourced from the **host's** `.env`, twelve lines further down, by the remote shell. The two have no bearing on each other. It was invisible for as long as both happened to be set; retiring the laptop copy made it fire on every deploy while the fields it warned about came back perfectly. The check now lives in the `else` arm of the remote command, where its subject is and where the answer is knowable. **A check sited on the wrong machine is not wrong until the two machines disagree**, which is also why it survived a rewrite of that exact block on 2026-08-25.
- **`npm run test:rotate-secret` covers the half that CI can reach.** Every refusal — no variable, an unrotatable key, missing deploy config — plus the preflight warnings, asserted by running the script with dummy `DEPLOY_*` and `--dry-run`, which exits before the first ssh. Its prove-red arm deletes `METRICS_TOKEN` from `compose.yaml` and requires the refusal, with a control asserting the restored file is byte-identical. The host-side half cannot be tested from a runner for the same reason `test-caddyfile.mjs` cannot run Caddy, and its controls are inside the remote script instead. The revocation probe was falsified by hand against the live host before being trusted: run with the **current** token it says `STILL_ALIVE`, with a token that never existed it says `DEAD`. A verdict only ever seen to say `DEAD` would also say `DEAD` if the curl failed or the field were renamed.
