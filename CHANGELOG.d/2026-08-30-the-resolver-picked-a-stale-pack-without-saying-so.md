---
date: 2026-08-30
title: "The fixture resolver picked a six-day-old pack and said nothing"
---

- **`npm run verify` gated one pack on this laptop and a different one in CI, from the same command (OA-180).** `.env` aimed `FIXTURE_DIR` at `Areas/St Ives/S5-render/v6.55_2026-08-24_1603`; the committed fixture had been refreshed from `v6.59_2026-08-30_0606` six days and four versions later. CI has no `.env`, so it gated the current pack. Nothing anywhere printed the difference — it surfaced as a side effect of the widened self-sufficiency gate reporting that the fixture's own `gen_external.js` byte-matched **neither** vendored candidate, which is the only line in the system that noticed.
- **`resolveFixtures()` now says so** — `warnIfBehindCommitted()` in `scripts/lib/fixture-freshness.mjs`, called from the resolver rather than from any one gate. Six scripts resolve fixtures; the fault is a property of the resolution, and a check each caller has to remember is one a seventh caller will not make. It prints both packs' `builtAt`, names the town, and says how to repoint.
- **It compares `build-meta.json`, NOT mtimes, and that is the whole design.** A committed fixture in a fresh clone carries checkout mtimes — every file "modified" the instant git wrote it — so an mtime comparison would report every live render as behind, on every clone, for ever. `builtAt` is content: it travels through git and says when the pack was generated. Where either side lacks it the answer is *cannot tell*, and that is printed rather than swallowed; a resolver going quiet when it cannot compare is how this row came to exist.
- **A warning, not a failure, and deliberately so.** Pointing the local gate at the live render tree is the STRONGER choice — that tree is where a regression surfaces first — which is why the environment still wins over the committed fixture. What failed here was not the choice but the silence. The existing `warnIfStaleSibling()` could not have caught it: it asks whether a newer render sits beside the fixture inside the same tree, and the committed fixture is nobody's sibling.
- **Falsified before it was trusted** — `npm run test:prove-red-fixture-drift`, wired into `verify.yml` ahead of the three gates, ~2 s, no fixture repository needed (seven scratch trees under the temp dir). Two cases must make it speak; **five must keep it silent**, which is the harder half: a warning that fires on a current fixture, on a fixture that is legitimately AHEAD of the committed pack, on the two towns in `verify:defaults` that have no committed fixture at all, or on the CI shape where `FIXTURE_DIR` is unset, is a warning nobody reads by the end of the week. Watched red under three separate mutations — the call removed, the direction test removed, the counterpart check removed.
- **The control asserts what a verdict cannot: the resolution is unchanged.** An advisory check that quietly repointed a fixture would have destroyed the very property the env override exists for, and every assertion about warning text would still have passed.
- **One assertion was being satisfied by the wrong clause, and only the mutation found it.** *"the warning names the town"* read the child's whole output — which included the resolved fixture path in JSON, so it stayed green with the warning deleted entirely. The harness now strips the `RESULT` line before asserting on what the resolver said.
- **An explicit identity guard was written, mutated, found dead, and removed.** The case it claimed to handle — `PLACE_FIXTURE_DIR` pointing straight at a committed fixture, which is how this laptop is set up — was already answered one line later, because such a path's "town" reads as `_portal-fixture` and no committed fixture is called that. Removing the guard changed no case in the harness, so it went rather than staying in looking load-bearing.
- **`.env` repointed to the three current renders** (St Ives `v6.59`, Huntingdon `v3.47`, Beaconsfield `v1.50`, all built 2026-08-30) and `verify:area` re-run: byte-identical on all four sheets. That edit is per-machine and cannot travel in git, which is why both halves of it are now written down in [`docs/DEVELOPING.md`](docs/DEVELOPING.md) beside the other `.env` keys and in `.env.example`.
- **Two documents were stale in the same place and were fixed with it.** `DEVELOPING.md` still described the gates as exiting 0 with "skipping" when the variables are unset — untrue since 2026-08-20, when they began failing instead — and `R1-create-map.md` still told the reader that a PowerShell env-prefix mistake makes `verify` skip silently, when what it now does is silently gate the committed fixture instead: a real gate, but not the map being onboarded.
