title: "The organisation page would not say which URL it was — and the rule that should have caught it was half-enforced"
---

`/o/:slug` ended in a bare `reply.sendFile('org.html')`, so it served the raw shell: `<title>An organisation's bus maps — BusMaps.uk</title>`, a matching static description, and **no `<link rel="canonical">` at all**. Every other public page goes through `sendShell()` with a computed head. Measured against the live site on 2026-09-08, 47 of the 48 URLs in `sitemap.xml` were perfect and the 48th was this one. It now gets an `orgHead()` beside `mapHead()`: a per-organisation title, a description carrying the organisation's own name and its published map count, the canonical, and the three `og:` tags.

- **The rule was already half-enforced, which is the part worth keeping.** `org.html` has been in `SERVER_FILLED_SHELLS` since 2026-08-31 — "the three shells whose `<head>` is completed SERVER-side" — and `test-indexing.mjs` asserts that each of those carries no canonical of its own, *because the server injects one*. For this page the server did not. Two things are true of those shells; one was checked and the other was remembered, and the checked half is the one that makes the page worse on its own. A page with no canonical is at least consistent; a page forbidden to carry one, served by a route that supplies none, is the fault.
- **It is silent today and that is why it sat there.** With one organisation there is nothing for `/o/busmaps-uk-pilot` to be a duplicate OF, so it reads as *no problem* rather than as *this check is not running*. On the second organisation, two pages would arrive at a crawler with the same title, the same description and no statement of which URL is authoritative — and the page's content is filled in by JavaScript after load, so there is nothing else to tell them apart.
- **`npm run test:sitemap` asks the question nothing asked: of the URLs this site OFFERS a crawler, does each one answer, and does each one say which URL it is?** `check-live-routes.mjs` asks whether every route in the table still answers; `test-indexing.mjs` asks what `robots.txt` says and whether each hand-written page carries its own canonical. Neither asks the join, and the join is where the fault was. **The population is the sitemap's own**, so a thirteenth static page or a second published map joins the check on the day it is published.
- **It seeds TWO organisations on purpose.** The duplicate-identity half of the rule is the half a live site with one organisation cannot show, so the laptop asserts it and the live check reports it as an observation while saying, in its own output, that it is not asserting it there.
- **`npm run check:sitemap` asks the same rule of a deployed site**, through the same judgement — `scripts/lib/sitemap-heads.mjs` is shared, so the laptop and busmaps.uk cannot reach different conclusions about the same page. Run against the live site before this fix, it reproduced the hand measurement exactly: **50 URLs advertised, one fault, and it was `/o/busmaps-uk-pilot`.**
- **`prove-red-sitemap.mjs`: six mutations, six caught for their own reason, control green.** The organisation page back to a bare `sendFile` (the original fault), every organisation page given the same title again, an organisation canonical on the wrong host, the same on a MAP page — because the rule is about every shell the server fills and not about the one that happened to be broken — the shell's own `<title>` surviving the splice, and **the sitemap ceasing to advertise organisations at all**. That last arm is the one that matters: the check's population is the sitemap itself, so a subject that disappears would otherwise take every assertion about it quietly green.

`npm test` **84 run, 0 failed, 2 excluded**. buses-data OA-284.
