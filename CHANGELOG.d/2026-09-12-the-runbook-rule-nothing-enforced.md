---
date: 2026-09-12
title: "SCHEMA_VERSION had a runbook rule and no enforcer, and a migration shipped with it stale the same day"
---

`docs/DEPLOY.md` has said **"Bump `SCHEMA_VERSION` in `src/db/index.js` when you add a migration"** since the constant was introduced, and nothing checked it. This morning the sample-band change added `ALTER TABLE customer ADD COLUMN is_sample` and left the constant at 4. Eighty-odd tests passed. A person re-reading the runbook before deploying was the only thing between that and a release whose database says it is a generation it is not — which matters because the boot path reads that row back, and a database written by a NEWER release than the running code logs a warning naming both numbers. That warning is the one signal a rollback produces, and a constant left one behind means it does not fire in exactly the case it exists for.

**`scripts/test-schema-version.mjs` now joins the numbered version blocks above the constant to the migrations below it.** It reads the source as text and opens no database: the blocks must run 1..N with no gap and no duplicate, `SCHEMA_VERSION` must equal the highest, and every `ALTER TABLE … ADD COLUMN` in `migrate()` and every `CREATE TABLE IF NOT EXISTS` — the three shapes this schema has ever grown by, and what versions 3, 4 and 5 are respectively made of — must be named, in backticks, by some block.

**The one judgement is the pre-v1 baseline and it is declared rather than computed.** Version 1 is defined as "the schema as it stood on 2026-08-25" and names no individual column, so thirty-one columns and tables predate any block and are listed in the checker with that reason beside them. Each was dated off `git log -S` before it went in rather than assumed from where it sits in the file — the newest is from 2026-08-12 — so nothing added after the constant existed is being excused by the list. The list is held in both directions: an entry naming a subject that no longer exists is a finding, and a baselined subject that a block also describes is a finding, so it cannot rot into coverage it does not have and cannot be reached for to silence a real one.

**Two bugs in the check were found by its own harness rather than by reading it, and both are the same shape — an assertion that could not fail.** Matching a column by its bare name let block 4's prose about a *rule* ("refuses an adviser a `customer_id`") claim two columns from July that it has nothing to do with; a column must now be written qualified, `customer.is_sample`. And asking whether a version number appeared twice by de-duplicating a Map's keys asked nothing at all, because the second block had already overwritten the first — the harness caught that by going red on the wrong assertion, not by going green. `scripts/prove-red-schema-version.mjs` breaks twelve things one at a time, requires each to go red on the right assertion, and keeps the exact regression — a new `ALTER` with the constant left where it was — as its first arm.

`scripts/test-schema-compat.mjs` sits beside it and asks a different question: whether the rollback PAIR opens. That answer is the same whether the constant was bumped or not, which is why it was green this morning.
