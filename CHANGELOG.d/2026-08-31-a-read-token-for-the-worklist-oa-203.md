---
date: 2026-08-31
title: "A read token for the worklist, and the standing laptop cookie it retires (again)"
---

Peter asked why the bus-work worklist needs a `cbm_session` cookie that keeps expiring when delivery and deploys never ask him for anything. The answer was that it is not a shorter credential, it is a different door — and following it back found a remedy this repository had already applied and quietly lost.

- **The asymmetry.** `npm run deliver` and `npm run deploy` go over **SSH** and write SQLite inside a throwaway container; `push-status.mjs` carries `STATUS_TOKEN` in a Bearer header. None of the three touches the web app's authorisation at all, and none expires. The worklist reads two admin routes over HTTP — `GET /api/admin/worklist` and `GET /api/maps` — and the only credential this portal issues for a **person** is a magic-link session. So it borrowed one.
- **`OPERATOR_TOKEN`, read-only.** Third instance of a pattern already here twice (`METRICS_TOKEN`, `STATUS_TOKEN`): Bearer header only, constant-time, its own variable, unset means nobody. It admits those two GETs at admin scope and nothing else anywhere. **Its own variable deliberately** — the argument written above `POST /api/admin/status` is that separate credentials stop a read token becoming a write token, and sharing that one here would have run it backwards, since `STATUS_TOKEN` *writes* the snapshot the worklist then trusts.
- **The method check inside `operatorRead()` is the design, not decoration.** Read-only is a property the function holds on its own rather than one that depends on nobody ever adding a third call site in a POST handler. It is also the one part of this change that could have been a constant wearing a condition — both real call sites are GET handlers, so a guard that never sees a POST is indistinguishable from `return true` until something makes it see one. `prove-red-operator-token.mjs` makes it see one: two of its arms differ by exactly that line, and measured, the pair behaves as claimed — with the guard intact every write stayed refused, and with it removed the token invited itself an admin account.
- **The forbidden-route list is a sample, so the real claim is asserted against the source.** A list of routes the token must not reach can only ever cover the ones somebody remembered — this project's own CSRF hook says it best, and the rule it states is that a rule applied by enumeration is right on the day it is written. `scripts/test-operator-token.mjs` therefore also asserts that `operatorRead` is *defined once and called exactly twice*, and names both call sites. A mutation that adds a third one, on a route no list mentions, is caught by that assertion and by nothing else.
- **What it replaces, and the finding worth keeping.** The 2026-08-20 P1 block closed audit item S5 with sliding sessions, step-up and a revoke screen, and its entry here ends: *"Together these retire the standing admin cookie kept in a file on the laptop."* Eleven days later that practice was documented back into existence — in the **skills** repository, by a change that was right for its own reason (the worklist had been silently opening the dev checkout) and that stopped it guessing by telling the operator to paste a live `cbm_session` value into `.env` and leave it there. Nothing detected the reversal, because the remedy lives in a changelog fragment here and the reinstatement lived in a skill there, and neither names the other. **A cross-repository remedy has no gate; the only thing that ever catches one is somebody asking why a thing behaves the way it does.**
- **What it deliberately does not do.** The operator half stays browser work: accepting a staged refresh, withdrawing a publish request and changing a map's outputs are writes behind a real session, and publishing plus the three settings routes are behind the 30-minute step-up, which a stored credential fails **by construction** and should. `--cookie` / `BUSMAPS_COOKIE` still works and is no longer the recommendation.
- **Also worth writing down, because it was the actual diagnosis.** The cookie is not short-lived — `SESSION_DAYS = 7` and the window slides on use, so every live worklist run renews it by a week. What kills it early is signing out in the browser, since the value in `.env` is the very token that click deletes.
