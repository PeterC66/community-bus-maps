title: "The schema says what its comments said, and one place reads a timestamp"
---

OA-224 Tier 4.5 (portal-src F9, F11, F12) and the portal's half of Tier 5 (cross-repo F15 and F23, portal-ops T7).

**F12 — the two state enums are the database's rule now, not a `--` comment.** `map.status` has six legal values and `map_version.review_state` five, and `schema.sql` carried 15 `REFERENCES`, no `CHECK` and no index. A handler writing `Published` or `pubished` was accepted by the database, failed no test, and took the map off the public site, because every public query filters on that exact string.

- **Triggers rather than `CHECK`, and SQLite is the reason.** A constraint cannot be added to an existing table. A `CHECK` means the twelve-step rebuild, and this database runs with `PRAGMA foreign_keys = ON` across the one CIRCULAR reference in the schema — `map.published_version_id` points at `map_version`, `map_version.map_id` points back. A `BEFORE INSERT`/`BEFORE UPDATE` trigger raising `ABORT` is additive, reversible by `DROP TRIGGER`, visible in `sqlite_master`, needs no data movement, and leaves `docs/DEPLOY.md`'s rollback promise exactly as it was.
- **The lists live in `src/db/enums.js` and the triggers are rebuilt on every boot**, not created once: the trigger body carries the value list, so a list that gains a value has to reach the database. `CREATE TRIGGER IF NOT EXISTS` would leave the previous release's rules enforced for ever on every database that already had it.
- **A trigger cannot refuse a row that is already there**, which a rebuild's `CHECK` would have. So the migration asks that question separately against the real rows and answers it out loud — a warning, not a throw, on the same argument as the schema-version notice beside it. Watched: a database with a deliberately corrupted `status` boots, names the value and the count, and keeps serving.
- **`scripts/test-db-constraints.mjs` asserts both directions and the comment.** That the guard refuses the illegal, that it **accepts every legal value** — a trigger with a typo in its own list passes the refusal test perfectly while making a legal state unwritable — and that `schema.sql`'s comment still names exactly the values `enums.js` names, in the same order. Moving a list out of a comment creates a second copy of it, and a second copy is an improvement only if something joins the two.
- **Two indexes, and two the review asked for that are deliberately absent.** Each addition was measured with `EXPLAIN QUERY PLAN` against a copy of the real database: `idx_map_customer` and the partial `idx_map_published` each turn a `SCAN` into a `SEARCH`. `map_version(map_id)` is *already* an index — `UNIQUE (map_id, major, minor)` gives SQLite one, and the per-map version query already reported `SEARCH … USING COVERING INDEX`. `audit_log(map_id)` indexes a query nobody runs: `listAudit()` orders by `a.id DESC LIMIT ?` and takes the primary key. An index with no reader costs write time for ever and hides the ones that earn their place.

**F11 — one reader of a stored timestamp, and the storage format is deliberately unchanged.** The conversion from SQLite's `2026-09-03 01:23:45` to a JS instant was hand-written at nine sites in five files, and only one of them checked the shape before converting. `src/db/dates.js` holds `parseDbDate`, `dbDateToIso` and `dbDateMs`.

- **The plan asked for the values to be stored as ISO, and two measurements say no.** It would break the documented rollback: older code runs `String(v).replace(' ', 'T') + 'Z'`, which on an already-ISO value gives `…ZZ` and an **Invalid Date** — rendered in this codebase as an empty string, so every date on every screen would silently go blank. And any mixed state sorts wrongly, which is what a migration that fails part-way leaves behind: `T` is `0x54` and a space is `0x20`, so in the plain string comparison SQLite does on TEXT, an 11pm row in the old form sorts **before** a 1am row in the new one — silently, and in the direction that puts the newest row at the bottom of a list somebody is reading to find out what just happened. Both are re-measured by the test, so the reasoning cannot go stale without saying so.
- **The census is the half that lasts.** Testing the helper proves it is right; it says nothing about whether anybody uses it. The duplication was not a bug in any one of those nine lines — each was locally correct on the input its author had in mind — it was a bug in there being nine.
- **A second census arm was written, run, and removed rather than shipped.** It flagged any literal `datetime('now')` outside `db/`, and its first run produced two findings, both false: a comment explaining that `expires_at > datetime('now')` compares correctly as strings, and the query doing exactly that. A `datetime('now')` in a `WHERE` clause is the clock, not a stored value, and a rule that cannot tell a comparison from a write would sit red on that line for ever. A check that produces false findings is muted within a week, and then it is not protecting the true ones either.

**F9 — camelCase at the boundary, and a shim that is dated rather than forgotten.** `mapDetail().versions[]` emitted `storage_key`, `review_state` and `created_at` straight out of the database, beside siblings called `currentVersion`, `hideOperatorsEnabled` and `headState`: one payload, two conventions. `docs/CONVENTIONS.md` now states the rule — snake_case is the database's spelling, camelCase is the API's, and `versionKey` is the API's name for `map_version.storage_key`.

- **Both spellings ship for one release**, because `views/app/editor.html` loads `/app/editor.js` with no cache-busting query: a browser holding the previous file is an old client against a new server, and a clean rename would break the editor for exactly the customers who had used it most recently. `scripts/test-map-detail-keys.mjs` asserts **both** sets and names the condition for dropping the old ones, so removing the shim is a failing test rather than a comment somebody has to notice — the lesson from the 404 discriminator one day earlier, where a shim was preserved in wording and broken in position because only one half of it was asserted.

**And a landmine found while gating this, one commit away from going off.** `scripts/test-schema-compat.mjs` copies the previous release's `src/db/` out of git and runs it, and it copied a hard-coded two-item list. `src/db/index.js` stopped being self-contained on 2026-09-02, when Tier 3.3 gave it `../hash.js` and `./paths.js` — the test kept passing only because `refs.previous` still pointed at a commit *before* that split. The very next change to `src/db/` would have turned every arm of the rollback test into "cannot find module", and it would have looked like that change's fault. The file set is now **read out of the old commit** by following its relative imports transitively: at the current previous it resolves 2 files, and at the Tier 3.3 commit — the next one it will use — it resolves the 4 the list would have missed.

**Tier 5's portal half.**

- **The conflict-marker refusal, and this repository was carrying the fault when it landed** (cross-repo F23). The check was written in `buses-data` on 2026-08-31, motivated by an incident *here*, and never copied across; `.githooks/pre-commit` was a 49-line strict subset of the other's 169. Rebasing #211 found `main`'s `CHANGELOG.md` carrying three committed conflict-marker lines with a stale duplicate docstamp beneath them. Git does not stop this — it refuses a commit only while a merge is *in progress*; once the file is staged it commits whatever is in it — and the shape that produced it is a generated file whose generator does not rewrite its own header, so `npm run changelog` reported "index is up to date" with the markers still above the block it rebuilt. **It is FIRST in the hook on purpose**: the stamper block below it exits 0 early when the `stamp-docs` tree is absent, which is right for the stamp check and would have silently disabled this one everywhere that tree is missing. Watched four ways — refused unpiped, still refused through `| head -4` (the pipeline hole that once let a refusal exit 0), still refused with the stamper absent, and green on the resolved file.
- **One Node pin** (cross-repo F15). `engines` said `>=22` against a `node:24-slim` image and three workflows on 24 — a floor nothing had ever run, and the only one of the five pins a person reads before installing a toolchain. `scripts/test-node-pin.mjs` reads the major out of the Dockerfile and requires `engines` and every literal workflow pin to match, while deliberately **not** requiring `verify.yml` to spell it out, since that workflow already derives it. Watched go red on the real `>=22` before the fix.
- **`README.md` stopped enumerating what `npm test` runs** (portal-ops T7). It described two phases' worth of checks for a suite that discovers 57 files. The count comes off the run now.
