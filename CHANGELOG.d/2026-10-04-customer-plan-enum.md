date: 2026-10-04
title: "A customer's plan is a choice, not a typed word"
---

- **`customer.plan` is now `free` or `managed`, and nothing else.** It was a free-text box on the admin Customers screen, and `managed` is the one value the portal reads: it silences five customer emails and makes a publication ask for the customer's emailed yes. A typed `managd` quietly made the customer non-managed and the portal then emailed somebody Peter had promised would hear only from him. The list lives in `CUSTOMER_PLANS` in `src/db/enums.js` and joins the three state enums under the same trigger guard.
- **It is chosen at approval.** The approve dialog has a "How we serve them" choice, defaulting to `free`, so a managed customer is made managed in the one step that creates them and not by remembering to type a word afterwards. The Customers screen's Plan column is a two-option select. A caller that sends no plan behaves exactly as before.
- **A bad plan is refused with the legal list at every door.** `PATCH /api/admin/customers/:id` and the approve route answer 400 naming `free, managed` and save nothing; `updateCustomerAdmin` throws instead of dropping the value as its `status` sibling does; the database trigger is the backstop. A stored value that is not on the list shows as "Choose…" so saving that row forces a decision.
- **One tidy migration, schema version 7.** On first boot any stored plan that is a legal value in another spelling (` Managed `, `FREE`) is put in its canonical form before the guard goes on, because the guard would otherwise refuse every later write to that row. A value that is not a spelling of a legal one is left alone and named in a `[migrate]` warning, never guessed at. Idempotent, and it changes no behaviour: `isManaged()` already read these rows as it will now.
- **Tests.** New `test:customer-plan` runs the migration for real in two child processes against one database file, then checks the database, the helper, the admin PATCH and the approval route, each with a control. With `customer.plan` removed from the enum list it goes red on six checks. `test:notify`'s old case that a typed ` Managed ` still counts now says the spelling is refused and the customer is still managed. `prove-red-schema-version.mjs`'s literals moved from 6 and 7 to 7 and 8.
- **Deploy history, written before the deploy per [DEPLOY §3b](docs/DEPLOY.md#3b-the-deploy-history-entry-is-written-before-the-deploy-and-merged-with-it).** This pull request's merge is the commit that goes live. It adds schema version 7 and no column or table: the boot rewrites padded plans and installs two triggers. **Rollback is not as clean as the last few versions**: a v6 release opens a v7 database and reads every row as before, but its Plan box is still free text and the trigger will refuse a value off the list with the database's own message. Read the first boot's log for `[migrate] customer.plan holds` — any line there names a customer whose plan needs choosing on the Customers screen.
- **Not changed, and worth knowing.** Approving an application as `managed` still issues the sign-in invite, because the invite is not one of the five suppressed emails. That is how the portal was designed, but it sits awkwardly beside "the portal emails a managed customer nothing" and is raised for a decision.
