title: "The require scan had gone blind to the way two generators ask for a module"
---

`Development Docs/open-actions.md` in `buses-data`, OA-129 Phase 3.

- **`gen_internal.js` was re-vendored carrying four new requires that were not in `engine/`, and `check-vendored.mjs` said "every module they require is here".** The four are `strict_guards.js`, `poi_select.js`, `fit_set.js` and `projection.js`, extracted from `gen_internal.js` upstream on the same day. Each is required at LOAD, so the portal would have thrown `MODULE_NOT_FOUND` on the first internal render of any map — area or place — anywhere the skill tree is not on disk, which is every machine that matters. It did not fail here only because the generator's own last-resort fallback is a hardcoded path into the skill checkout, and this laptop has one.
- **The cause is that the scan recognises a dependency by finding the module NAME as a literal beside `SKILL_ASSETS`.** `gen_boarding.js` has always factored its resolver into a `_dep(name)` helper and called it with the literal, and `gen_internal.js` joined it in the same refactor. In that form the only thing beside `SKILL_ASSETS` is the parameter, so the pattern matched nothing at all and the file was reported as requiring nothing. `gen_boarding.js` had been invisible this way for as long as it has used `_dep`; `gen_external_places.js` writes a third form — `if (…) return path.join(…)`, with no `?` — that the pattern also never matched.
- **The scan now knows all three forms**, and the `&&` candidate-list form stays excluded on purpose. Widening the first pattern far enough to catch `_dep` also caught `diagram_internal.js` and `schematize_internal.js`, which name `gen_internal.js` as one of three candidates that `existsSync` chooses between and which report their own miss. That would have opened the check red on two known-good files on day one, which is how a check gets muted rather than fixed — so the exclusion is written down beside the patterns rather than discovered again.
- **Watched go red before being trusted.** With the fix in, the check named exactly the four missing modules and nothing else; with the `_dep` pattern taken back out, `scripts/test-vendored.mjs` fails on the case that matters. Four new assertions cover the three idioms, and a fifth asserts the `&&` form is still not flagged.
- **The four modules are vendored, listed and byte-checked.** `engine/vendored.json` gains four rows written by hand, because the manifest is the vendor script's input and it cannot invent a row for a module nobody has listed — a limit that script states about itself. `npm test`, `npm run verify:place` and the skills-side board are all green, and the board's `place/gen_internal.js` and `expert/gen_boarding.js` rows are back in sync.
