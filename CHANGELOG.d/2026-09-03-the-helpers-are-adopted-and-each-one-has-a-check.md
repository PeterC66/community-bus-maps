title: "The helpers are adopted, and each one now has a check saying its callers use it"

buses-data [OA-232](https://github.com/PeterC66/buses-data/blob/main/Development%20Docs/open-actions/OA-232.md) Tiers 1 and 2, the portal's half. The 2026-09-03 codebase review found the same shape in eight helpers at once: **a helper that lands with a test of ITSELF and no test of its callers is adopted wherever its author happened to look, and nowhere else.** The two Tier 3 helpers that ARE fully adopted — `gate_lib.findSheets` and the route table — are exactly the two whose arrival came with a test that the callers *are* the helper. So nothing here is a new extraction. Every item is an adoption plus the check that keeps it adopted.

**One HTML escaper, and a census with an allowlist that has reasons in it (portal-src F26).** `src/html.js` landed on 2026-09-02 as "the one escaper for server-built markup". A day later it had two importers, while `server.js` carried a private `escapeHtml` and a four-character `htmlAttr`, and `src/public/shell.js` a third copy. All three are gone. `attr` keeps its name in `shell.js` because the intent at the call site is attribute-position; it is now `escapeHtml`, which also escapes `'` — a superset of what an attribute needs, and the only visible difference is `&#39;` where a value holds an apostrophe. `scripts/test-ssr.mjs` now walks `src/` and refuses any file that defines its own. The allowlist is the honest part: three files write SVG text where the HTML entity set is wrong and one writes `sitemap.xml` with `&apos;`, so each is named with its reason rather than the rule being loosened — a blanket rule would have been red on day one over five legitimate sites, and a check that is red on day one is muted inside a week. **The list also insists every entry is still a file that still carries an escaper, and that case went red the first time it ran**, on an entry I had listed as a decoder — true, and exactly why the pattern never matched it, so the entry was widening the allowlist for nothing.

**`NOW_SQL` has callers, and the arm that was removed as unworkable is back because the constant was wrong, not the arm (portal-src F27).** `NOW_SQL` was exported on 2026-09-02 to be the one spelling of the database's clock and had **zero** callers against 31 literal `datetime('now')`. `test-db-dates.mjs` recorded, at length, that a census arm over that literal had been written, run and REMOVED, because its two findings were both `WHERE expires_at > datetime('now')` comparisons and "a rule that cannot tell a comparison from a write would sit red on that line for ever". The reasoning was right and the conclusion was backwards: what made the arm produce false findings was `NOW_SQL`'s own docstring, which said *"what goes in an INSERT/UPDATE"* and so excluded the very sites the arm reported. One word in `dates.js` dissolves it. The constant is the clock — in reads as well as writes — `db/index.js`'s fifteen sites and `ops/index.js` import it, the comment in `auth/index.js` names it, and the arm is in the suite. It was measured, not assumed: the arm went in before the last site was converted and reported it.

**A backup can no longer migrate the database it is about to copy (portal-ops D6).** `scripts/backup.mjs` took `DATA_DIR` from `src/db/index.js`, which applies `schema.sql` and runs every migration at module load. Repointing that one import at `src/db/paths.js` — the fix as the review stated it — is only a third of the chain: `dirSize` came from `src/ops/index.js`, which imports `db`, and `src/maps/store.js` took `DATA_DIR` the same way and kept its own second spelling of `MAPS_DIR`. All three moved; `dirSize` is now `src/ops/dir-size.js`, re-exported from `ops/index.js` so no importer changes. **`test-portal-lib.mjs` reads the module list out of `backup.mjs` itself** rather than naming three, loads every one in a child process with a scratch `DATA_DIR`, and asserts nothing is created — watched go red by adding an `import { db }` back, and green when it was removed.

**The vendored-engine audit runs on every `npm test` (portal-ops T8).** `check:vendored` — UNLISTED / MISSING / EDITED / UNRESOLVED — ran in no workflow and was no preflight; the only thing exercising `auditVendored` against the real tree was one section of `test-vendored.mjs`. It is a fourth preflight in `run-tests.mjs`, as `--no-skills`, the form CI can run.

**And that fourth preflight broke the harness that guards the runner, which is the finding worth keeping.** `prove-red-run-tests.mjs` builds a scratch repository, and it wrote stubs for a TYPED list of three preflights — eight lines above a comment explaining why the `EXCLUDED` list is read off the runner and not copied, "so this harness cannot go stale when one is added". Six of its assertions failed with `MODULE_NOT_FOUND`. The same lesson, applied to one list and not to its sibling. Both are derived now, and so is the `6 run` count that the fourth preflight also falsified.

**One run per ref (portal-ops W2), and two prove-reds that ran twice per push (W6).** None of the four workflows had a `concurrency:` group, so a second push to a branch left the first run going and a stale run could finish last and be the verdict a reader sees. All four have one; `cancel-in-progress` is safe because none of these jobs writes anything outside its own runner. And `test:prove-red-fixture-drift` and `test:prove-red-engine-source` are out of `verify.yml`: `npm test` is a discovering runner since 2026-09-02 and `test.yml` runs it on every push, so the copies here were the redundant ones — and they were the ones behind the cross-repo PAT, which is the wrong place for two harnesses that need no fixture repository at all.

**Three strings and one bare path.** `check-vendored.mjs`'s header documented `skillRootDefault` in `engine/vendored.json` for a day after that key was removed from the manifest (portal-ops V4); the legacy read stays, deliberately, and `test-vendored.mjs` exercises it. `scripts/test-build-warnings.mjs` had `C:/u3a St Ives/Using AI/Buses/Areas` written into it with no environment read, so the half of that test which runs against the real corpus was silently off everywhere but this laptop (T6) — `scripts/lib/buses-dir.mjs` now answers that question once, env first then one named default, and `upcoming-report.mjs`'s own copy is gone. `deploy.mjs` ends by printing `npm run check:live-routes` (W7): everything the deploy script checks asks whether the process came up, and none of it can see a route that stopped being registered, because that does not throw — it 404s, quietly, to whoever asks next.

`npm test`: 58 run, 0 failed, 2 excluded.
