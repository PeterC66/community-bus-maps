title: "Branch protection is on, and the two settings that would have bricked the repo are off"
---
`gh api repos/PeterC66/community-bus-maps/branches/main/protection` answered **`Branch not protected`** for the eight days this repository had been public and therefore free to protect, and `.../rulesets` answered `[]`. Both now answer. `main` requires four status checks BY NAME — `audit`, `docs`, `test` and `verify` — with *Require branches to be up to date before merging* on and *Do not allow bypassing the above settings* on, so there is no direct push to `main` for anyone and an admin cannot merge past a red check. Auto-merge was enabled in the same change, because a PR must now carry `main`'s tip as well as four green checks, and the habit here was to merge by hand the moment the checks went green — on PR #264, with **eleven seconds** to spare between the last check completing and the merge.

- **Required reviews are `null`, deliberately, and this is the setting most likely to be added later by somebody tidying up.** `PeterC66` is the only collaborator and GitHub forbids approving your own pull request, so requiring even a single approval makes every PR permanently unmergeable, with no escape but disabling protection. It is off because it cannot be on, not because nobody got to it.
- **`render-parity.yml`'s two checks are NOT required, and must never be.** `deployment image (Dockerfile FROM)` and `ubuntu-latest (system fonts present)` sit behind a `paths:` filter, so on a PR touching none of `src/render/**`, `Dockerfile`, `package-lock.json`, `scripts/render-parity-probe.mjs` or `scripts/render-parity-baseline.json` the workflow never runs, the check run is never CREATED, and a required check that never reports sits at *Expected — waiting for status to be reported* for ever. Measured on the day rather than predicted: PRs #266 and #262 carried only the four checks, while #261, a `package-lock.json` bump, carried all six. Three of the five most recent PRs would have been permanently unmergeable.
- **What strict mode closed, and what it conspicuously did not.** It closed the ordinary staleness — a PR can no longer be green against a base two commits old, which is what *read the POST-merge run, not the PR's own green checks* was written about. It does nothing about the cross-repo form, because it governs staleness against THIS repository's base branch only while `verify.yml` checks out `buses-data` with no `ref:`. That gate is still measured against whatever is on that repository's `main` at the moment it runs, and the advice survives in exactly that narrowed form. **Do not record this change as having addressed it.**
- **Two things will block every PR when they happen, and bypass is off, so the escape is a person turning protection back off.** `CROSS_REPO_PAT2` expires **2026-11-22** and `verify` hard-fails inside twenty seconds without it. And a PR from a **fork** gets a red `verify` it cannot fix, because Actions secrets are not passed to fork pull requests and this repository is public — there have been no outside contributors yet, and "public" is eight days old.
- **The gate was watched refusing something before it was trusted.** PR #265 read `MERGEABLE` / `DIRTY` before the change and **`BLOCKED`** within a minute of it, being behind `main`; it was updated, its four checks re-ran green, and it merged as `ad778e2`. What has not been watched is a *failing* check blocking a merge, and a direct push to `main` being rejected — both follow from the same settings, neither has been seen, and they are reasoned rather than measured.
- **`docs/CONVENTIONS.md` is corrected here for the third time in one day, which is the point of the entry.** It first justified the advice with *branch protection is not available on a private repo without GitHub Pro*; that expired on 2026-09-03 when the repository went public. It then said the feature was available and simply not switched on; that expired the moment it was switched on. In between, a session read the file out of a feature-branch checkout cut before the first correction merged and reported an already-fixed paragraph as stale — quoting a document's CONTENT from a local checkout while quoting the repository's SETTINGS from the remote, so the authority of the `gh` half carried across the paragraph break to a stale `sed`. Read a document from the ref the finding is about, with `git show origin/main:<path>`, not from whatever branch the disk is standing on.
