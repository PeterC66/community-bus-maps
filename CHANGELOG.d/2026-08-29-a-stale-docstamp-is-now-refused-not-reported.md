date: 2026-08-29
title: "A stale docstamp is refused at the commit, not reported by CI"
---

- **The docstamp is written by a Stop hook, which runs at the END of a turn — so a commit made during the turn always carries the new content and the old `sha=`.** The `status` job's *Committed docstamps describe their committed content* step then correctly calls it stale. Whether any given commit goes red depends only on where the turn boundary happened to fall, which is why it has always looked intermittent and why it is not. It has happened here already: [#149](https://github.com/PeterC66/community-bus-maps/pull/149) is exactly this fault, three documents' worth, found by CI after the push. In the sibling `buses-data` repo the same fault took **10 of 15** gates runs red in a single day, and the maintainer had started asking whether the errors were expected — the stage that precedes a muted gate.
- **`.githooks/pre-commit` now refuses the commit instead.** CI reporting it minutes later is the wrong end of the problem: by then the commit is pushed and somebody has to decide whether a red run matters. The hook is tracked rather than left in `.git/hooks/`, so it is reviewable and travels with the repository, and it exits 0 when the `stamp-docs` skill tree is absent — a hook that dies on a machine without it teaches whoever hits that to bypass it permanently.
- **It reads the INDEX, not `HEAD` and not the working tree, and both alternatives are wrong for a different reason.** At hook time `HEAD` is the *previous* commit; the working tree may already have been fixed by the Stop hook while the staged copy is still stale. `check_committed_stamps.py --staged` hashes `:<path>` — what git is actually about to write.
- **Scope is deliberately narrow: only the `.md` files in the commit in front of you.** A document that was already stale is not this commit's fault, and a hook that refuses unrelated work gets `--no-verify`'d within a week.
- **Watched both ways before being trusted.** Staging an edited document without re-stamping refused the commit — exit 1, `HEAD` unmoved, change still staged — and the identical commit succeeded after `docstamp.py --all`. The falsification commit was local-only and was reset out.
- **`core.hooksPath` is local git config and does not travel with a clone**, so each clone and worktree needs `git config core.hooksPath .githooks` once. That is stated in `docs/DEVELOPING.md` rather than worked around, and it is why CI keeps its full audit: the hook guards whoever installed it, CI is the one that is always there.
