---
date: 2026-09-19
title: "`trustProxy: 1` trusted nothing at all, so every visitor shared one rate-limit bucket — the comment above it described Express's behaviour, not Fastify's"
---

- **`src/server.js` set `trustProxy: 1` and explained that `1` "trusts exactly one hop — the local Caddy — so req.ip is the address Caddy actually saw".** That is what a number means in Express. In Fastify it means the opposite: `getTrustProxyFn` answers a numeric option with `function () { return false }`, under its own comment *"Hop-count-only trust cannot validate the immediate peer. Fail closed so direct clients cannot spoof X-Forwarded-\* values by supplying enough hops."* Fastify's shipped test for it is titled **"trust proxy number ignores forwarded headers"**. So the value was exactly equivalent to `false`, and had been since it was introduced (buses-data OA-256).

- **The consequence was the one the value existed to prevent.** `req.ip` was the Docker bridge gateway for every visitor — compose publishes `127.0.0.1:5180` and Caddy runs on the host, so every request reaches the container from the gateway — which was measured on the host on 2026-09-06 and is what filed the action. `req.ip` has two consumers: the log, where masking an address that was never personal data was merely pointless, and `rateLimited()`, where `/api/apply`, `/api/contact`, `/api/public/feedback` and the sign-in POST were limited **in total rather than per person**. One abusive host exhausted the allowance for everybody.

- **The value is now `'loopback, uniquelocal'`, and it is a module.** `src/http/trustProxy.js` exists for the reason `loggableReq` does: a literal inside the `Fastify({...})` options can be asserted about only by reading the source, which is how a value that did nothing survived a month of green suites. Naming addresses rather than a hop count gives the semantics the old comment claimed — proxy-addr walks outwards from the socket and stops at the first untrusted address, so exactly the hops the proxy added are peeled. `uniquelocal` rather than the literal `172.18.0.1` because a Docker bridge is renumbered by Docker and a value correct only until the network is recreated fails silently and in precisely this way.

- **It does not reopen the hole `technical-audit_2026-08-19` S3 closed, and that is asserted rather than argued.** `true` trusts the whole chain and takes the leftmost entry — the value the client sent — so anyone could pick their own `req.ip` and rotate it. Under an address list they cannot: Caddy appends the real peer rather than replacing the header, so a spoof sits beyond the untrusted real client and the walk never reaches it. The same attack using a **private** address is asserted separately, because `uniquelocal` trusts private addresses and the obvious reading says it should work — it does not, trust being evaluated by position in the chain rather than by whether a string looks local.

- **The suite controls the peer, which is the only reason any of this is observable off the host.** A real local request cannot vary its socket address, so the broken value and a correct one are identical on a laptop and in CI, which has no proxy in front of it; `app.inject({ remoteAddress })` is what tells them apart. Eleven assertions in two levels: the first probes the constant, including the spoofing properties; the second drives the **real app** and asserts the consequence — twenty knocks from one visitor are refused on the twenty-first, and a different visitor still gets through. Neither level covers the other, and the second is the join that says `server.js` uses the constant at all.

- **Five mutations, each watched red for its own reason** (`npm run test:prove-red-trust-proxy`): the bug verbatim, `true`, dropping `loopback` from the value, and — the case the harness is really for — leaving the constant perfect and severing it from the server, which is the state the repository was actually in and which only the app-level assertions can see.

- **The `req.protocol` half turned out not to be a live fault, checked rather than assumed.** The archived `GO-LIVE.md` §2.4 warned that `authLink()` builds sign-in URLs from `req.protocol` and would email `http://` links. `baseUrl()` has preferred the configured `PUBLIC_BASE_URL` since the N5 account-takeover fix of 2026-08-25, and the live `sitemap.xml` emits absolute `https://busmaps.uk/` URLs — which it could only do if that variable is set, since `req.protocol` was provably `http`. `isHttps()` reads `x-forwarded-proto` directly and never depended on this either. The rate-limit bucket was the whole of the live damage.
