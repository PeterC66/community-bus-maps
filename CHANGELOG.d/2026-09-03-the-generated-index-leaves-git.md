---
date: 2026-09-03
title: "The generated index leaves git, because the split that was meant to end the conflicts had made them universal"
---

Peter, after the second changelog conflict of the day: *"is there any way we can get over the changelog conflict in future — it applies almost every time I do two sessions at once."*

**It did, and the reason is worse than it looked.** `CHANGELOG.d/` exists because `CHANGELOG.md` had reached 2,407 lines and 65 of the last 200 commits, and two sessions appending to it conflicted every time. The fix split the prose into one file per entry — and left the GENERATED INDEX committed. Every commit regenerates that index, so the contention did not go away: it moved onto one line and became **universal**. Measured: **60 of the last 60 commits touched `CHANGELOG.md`**, against 145 of 200 before the split. Portal [#215](https://github.com/PeterC66/community-bus-maps/pull/215) and [#216](https://github.com/PeterC66/community-bus-maps/pull/216) collided on exactly that line, and both sessions had declared their files to each other without either one naming it.

**Three documents said the opposite, in the same words.** `changelog-assemble.mjs`'s own header, `CHANGELOG.d/README.md` and buses-data's glossary all claimed the index was safe because it is sorted deterministically, "so two sessions regenerating independently produce identical bytes". False, and false on the day it was written: determinism means the same FRAGMENT SET gives the same bytes, and two concurrent sessions have different sets, by one file each. All three are corrected.

**So the derived file left git.** `CHANGELOG.head.md` is tracked and holds the prose; `CHANGELOG.md` is generated from it plus the fragments and is gitignored. Nothing derived is in git, so nothing derived can conflict — and the fragments, which are what anybody actually writes, never conflicted in the first place. `changelog:check` changed job with it: it used to ask whether a committed index was stale, which is a question about a file that no longer exists, and now validates the fragments — front matter, the filename agreeing with its own `date:`, and no two names differing only in case, **which are two files on this laptop and one on the Linux server**, so an entry would vanish there and nowhere else.

**The near-miss, which is now an assertion.** The Dockerfile carried `COPY LICENSE NOTICE README.md CHANGELOG.md ./`. A docker build context is the working tree, not git, so on this laptop — where the generator had just run — it would have built perfectly, and failed in CI and on any fresh clone. It now copies `CHANGELOG.d/` and `CHANGELOG.head.md`, and `test-changelog.mjs` asserts all three halves of that: the fragments are in the image, the generated file is not, and the template is.

**The admin `/changelog` page generates instead of reading.** It used to `readFileSync` the committed file, which after this change is not in the image at all — it would have degraded to "(not found on this instance)", a page that looks like it works and shows nothing. It now builds the list from the fragments on every request, which makes it **always current**: the committed index never was, being only ever as fresh as the last person who remembered to run the generator. The shared rules moved to `src/changelog.js` and the CLI imports them, rather than the route importing from `scripts/` — only `src/` ships in the image by contract.

**A git merge driver was built first, proved, and thrown away.** It worked: 20 assertions including a control that built the real two-branch collision and required it to conflict without the driver. It is still the wrong shape — not having a conflict beats resolving one, and it needed a `git config` line in every clone that git silently ignores when somebody forgets. Two things learned building it are worth keeping. **A merge driver cannot see the other side's new files**: measured in a throwaway repository, at the moment git invokes one, `git ls-files`, the working tree and `git ls-tree HEAD` all held OUR side only, and `git rev-parse MERGE_HEAD` failed outright because MERGE_HEAD is written *after* the merge attempt — so the first driver silently produced an index missing exactly the entry the merge was about, and passed "the merge succeeded" and "no conflict markers" while doing it. And **GitHub's server-side merge does not use local merge drivers**, so a PR would have gone on showing as conflicting whatever the driver did.

**One check was moved because it could not fail where it runs.** The case-collision rule started as a loop inside `entriesFromDir`, and the test for it could not build its own fixture: writing `2026-09-03-Good.md` beside `2026-09-03-good.md` on a case-insensitive filesystem overwrites the first, `readdir` returns one file, and the arm passed for the wrong reason on the only machine that runs it. It is now `assertDistinct(names)`, a pure function over a list, and the test asks it directly.
