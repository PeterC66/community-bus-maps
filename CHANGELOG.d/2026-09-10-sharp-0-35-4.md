---
date: 2026-09-10
title: "sharp 0.35.4 — the libheif advisory that reddened main, fixed rather than deferred, and the JPEG bytes proved unmoved"
---

Dependency only; no code changed. `dependency audit` had been red on `main` since the advisory was published, and was found on 2026-09-10 by a documentation PR rather than by the schedule.

- **The advisory is [GHSA-rgj7-g3m4-5g8c](https://github.com/advisories/GHSA-rgj7-g3m4-5g8c), high, CWE-122**, and it is `sharp` carrying two heap-overflow vulnerabilities in **libheif** — GHSA-g89c-p67h-r497 and GHSA-2jg2-4ch7-h545. Vulnerable range `<0.35.4`; we were on 0.35.3. `sharp` is a direct dependency, and `^0.35.3` already admitted the fix, so this is a lockfile bump plus a raised floor rather than a migration.
- **We were almost certainly not exposed, and the fix was free anyway.** libheif decodes HEIF/HEIC, and nothing here ever hands `sharp` an image it did not itself make: `renderMap.rasterise()` takes an SVG from the vendored engine, `webPreviewPath()` resizes a JPG the portal rendered, `watermark.js` reads that same JPG, and the `ops` health check builds an 8×8 buffer in code. There is **no upload path at all** — no `multipart`, no `multer`/`busboy`/`formidable`, no route that accepts an image — so no attacker-supplied bytes reach the decoder. That is a reason not to panic, not a reason to defer: an allowlist entry is a dated promise somebody has to keep, and this cost one `npm install`.
- **The bundled libvips moved with it, 1.3.2 to 1.3.3, and that is the encoder.** So the question worth asking was whether a rendered sheet's JPEG bytes changed — and `npm run verify` **cannot answer it**: its byte-identical assertion is about the regenerated **SVG**, which is pure JavaScript, and its JPG comparison is reported for information only. A green `verify` would have proved nothing about this bump.
- **Measured instead of assumed, on all four sheets of the committed fixture.** The shipped JPGs were rendered by the engine's `sharp@0.34.5`; the portal on 0.35.3 reproduced them byte-for-byte, and on 0.35.4 with the new libvips it still does — 1,250,716 B, 1,005,069 B, 1,131,863 B and 1,117,437 B, each `BYTE-IDENTICAL`, at 3508×2480. JPEG output is therefore stable across 0.34.5 → 0.35.3 → 0.35.4, so no stored sheet needs re-rendering and nothing downstream moves.
- **After the bump `npm audit --omit=dev` reports 0 of everything** and `scripts/audit-check.mjs` exits 0 with no deferral used.
