---
date: 2026-08-28
title: "The publish gate reads the S6 verdict, not just its date — and stops exempting places"
---

- **`scripts/lib/s6-freshness.mjs` now opens the run's own `verification.json`.** It used to answer one question — *was the map verified after its data last moved* — from a date comparison, and never the second one: *and did it pass*. So after the 2026-08-26 runs, the five towns that came back **BLOCKED** all reported `fresh` to `deliver-map.mjs` and would have been accepted as verified. Running the check is what put them there: before those runs they were at least STALE and deferred with an expiry. The gate reads `summary.verdict` (`pass` | `blocked` | `not-verified-uncurated-s1`), falling back to `summary.pass` for runs stored before that field existed on 2026-08-27, and its verdicts are now `fresh | stale | never | failed | unverified | no-verdict | not-applicable | no-manifest`.
- **The second half of the same bug was in the caller.** `gateS6()` consulted `scripts/s6-waivers.json` under a comment reading `// stale | never`, so a fresh-but-failing S6 skipped the deferral check entirely — those five towns were not merely accepted, they were accepted while carrying live deferrals that had silently stopped applying to them. The set of waivable verdicts now lives in `s6-freshness.mjs` as `REFUSING_VERDICTS`, beside the function that produces them, and `refuses()` is what the tests assert through. A verdict the gate does not recognise refuses rather than falling out of the bottom as a pass.
- **Every place is judged now, on the same terms as an area.** The gate returned `not-applicable` for any map whose `kind` is `place`, saying the place skill "has no independent-verification stage, so there is no S6 to be stale". Every clause of that stopped being true on 2026-08-08: `make-place-bus-leaflet` gained one via `place_verified_services.js`, the procedure is written up in the skill's `references/s6-verify.md`, and two places hold real runs. The tell was one line above the bug — `hasS6Runs` was computed from the manifest and the very next line returned without consulting it, the same shape as the `status.js` fault that left twelve sheet-gates decorative for their whole lives.
- **Ten places therefore start red, and arrive with dated deferrals rather than an exemption in the code.** Each one reads `never`, which is true of all of them. It is not a cheap debt: `redteam_source.js` answers **BUY** for all ten, because it only ever looks inside a build's own `S6-verify/` and a place has never had one, so none can reuse its parent town's answer — roughly a million tokens at the measured 89k–137k per red team. The `removeBy` on each row names the exact procedure, and the file's header records the cost so a reader can see what the deferral is deferring.
- **Two places needed no row, and they are the proof the rows can be retired.** St Neots Town Centre and St Neots Tesco Extra both read **PASS** as of 2026-08-28 (0 hard, 17 and 14 soft), after the map engine learned to tell a deliberately undrawn panel row from missing geometry.
- **Proved red before being trusted.** Restoring the previous `s6-freshness.mjs` under the new tests turns **eleven** assertions red, including the two that name each finding exactly: *a RECENT S6 that came back BLOCKED is not fresh* — got `fresh`; and *the same empty slot on a place is ALSO never, not exempt* — got `not-applicable`. That second assertion previously asserted the bug, which is what kept it alive. The suite also covers a report with no `verdict` field, one that is absent, and one that is unparseable — the last two must read `no-verdict`, never a pass, because `verification.json` is gitignored in the data repo and a fresh clone has none of them.
