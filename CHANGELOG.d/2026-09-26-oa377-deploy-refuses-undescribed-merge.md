title: "The deploy refuses a merge nobody wrote up"
---

- **`npm run deploy` now refuses to put live a commit that no deploy-history entry describes (buses-data OA-377).** Its new step 0 runs `git fetch origin main` and then `scripts/check-deploy-history.mjs`, before the backup and before anything on the host is touched. Every first-parent commit on `origin/main` after the baseline `9db6dd3` must add a `CHANGELOG.d/` fragment, edit `docs/DEPLOY.md`, or be named by `#NNN` or short sha in one of them. §3b used to order an entry only against its own change, and twice in September 2026 the merges in between went live described by nothing. Measured over the 85 merges from `7c7c710` to `9db6dd3`, the rule finds exactly one: #331, a fixture re-vendor, left behind the baseline as history. `npm run check:deploy-history` asks the same question without deploying.
- **New `scripts/test-deploy-history.mjs` (`npm run test:deploy-history`)** runs the checker against a throwaway git repository. Every way a commit can count as described is checked, and so is its red twin. It also checks the wiring: `deploy.mjs` must fetch, then check, then back up, in that order. With the rule broken on purpose (every commit counted as described), 7 of its 23 checks fail.
- **Deploy history, written before the deploy per [DEPLOY §3b](docs/DEPLOY.md#3b-the-deploy-history-entry-is-written-before-the-deploy-and-merged-with-it).** This pull request's merge is the commit that goes live, and it is the first deploy the new step 0 checks. The server does not import any of the changed scripts, so nothing a visitor or a customer sees changes: no schema, route, UI or engine change.
