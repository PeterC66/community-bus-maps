---
date: 2026-08-30
title: "A switched-off account, and a map with nobody to own it"
---

- **Disabling a user now ends the sessions they are holding, which it had never done.** `user.status` was tested in exactly two places — `requestMagicLink` and `verifyMagicLink` — and both are on the way IN. Nothing looked at it on the way through: `getSession` joins on the token and the expiry, `resolveUser` copies the status onto `req.user`, and `requireUser` / `requireAdmin` / `requireApprover` all test the ROLE. So switching an account off stopped that person obtaining a NEW sign-in link and left their open browser working — and because the seven-day window slides on use, a disabled person who kept working never expired at all. The admin console's own copy, "disabling is the reversible, audit-preserving equivalent" of a delete, was true about the record and silent about the credential.
- **The check went in ONE request hook, not in the three guards.** The guards are an enumeration, and this codebase had already argued that case against itself in the CSRF hook's header — a rule applied by enumeration is right on the day it is written and silent about the eighty-sixth route added next year. `/api/me` reads `req.user` directly and would have been missed by all three. Clearing it at the single site that SETS it covers every consumer that exists and every consumer that will. `/api/auth/` is exempt as a property rather than a path list: those routes only ever end a credential or ask for a new one, and a disabled person must still be able to clear their own cookie.
- **The dead credential destroys itself.** The refused session's row is deleted and its cookie cleared, so the two-step workaround — disable the user, then find and revoke each of their live sessions — is not needed and the Sessions tab stops listing a phantom. `PATCH /api/admin/users/:id` closes the same window from the other end at the moment of disabling and now reports the count, so the console says "signed them out of 3 live sessions" instead of leaving it to be trusted. `POST /api/admin/users/:id/revoke-sessions` had existed since the session work landed and was reachable from nothing; it is now *Sign out everywhere* on each Users row, for the other case — a credential that has leaked from an account that is staying open.
- **A map with no owning organisation is refused at import instead of noted.** `listPublicMaps()` and `getPublicMapBySlug()` both `JOIN customer`, which is deliberate — it is what makes a suspended organisation's maps disappear — and the same join silently drops a map whose `customer_id` is `NULL`. St Ives Bus Station was imported without `--customer`, went through submit → review → publish to v2.0, reported `status=published, public_listed=1`, and served a 404; the honest answer arrived two steps later from the accept-publish run's own public check. The importer now refuses before it resolves `--src`, naming the consequence, and `--unowned` is the deliberate way past.
- **`POST /api/admin/maps/:id/owner` is the repair that did not exist.** `user.reassign` had had an HTTP equivalent since P2 and the map had none, so the only fix for an unowned map was a hand-written `UPDATE` against the live database. Admin-only, step-up required, refuses a move that would overspend the receiving organisation's quota, and writes a `map.reassign` audit row.
- **Every refusal is paired with a control, and the suite has been watched go red.** `scripts/test-access-model.mjs` is 37 assertions; `scripts/prove-red-access-model.mjs` breaks eleven guards on purpose and requires the assertion named for each to be the one that objects. Two of those mutations break a *control* rather than a refusal — a hook that refuses everybody, a revocation that fires on every save — because a suite that only asserts refusals is green when the door is shut on everyone. The harness earned itself immediately: it found this suite asserting the importer's exit code first, which stayed green with the refusal removed because the same run then exited 1 on `--src not found`. The existing `test-audit-p1.mjs` covers a disabled user *signing in* and would have stayed green through every fault above.
- **Four documentation claims were wrong in the way that survives review** — the sentence still parses and the reader cannot tell. `R2-onboarding.md` and `Pol1-vetting-and-quota-policy.md` linked to `customer-register.md` and `vetting-decisions-log.md` in the ops folder, which were renamed to `P1-` and `P2-` on the other side; nothing in either repository can check a link into a folder that is in neither. `H2-todo-quickstart.md` said sessions last 30 days, which has been 7 since 2026-08-20, with `H1` §3b correct all along. And `R2`'s *What-if* row said suspending a customer means "they keep their data but lose access" — suspension removes their maps from the public site and does not stop a single one of their users signing in or editing. That last one is the expensive one: it is the row a reader consults on the day they most want to be sure, and it told them access had stopped when it had not.
