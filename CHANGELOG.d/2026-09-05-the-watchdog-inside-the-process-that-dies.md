title: "The watchdog inside the process that dies, and the supervisor that replaced it"
---

buses-data OA-052, the render-parity hang, after its eighth occurrence.

- **The eighth hang answered the question the seventh could not.** Run `33750970921` (2026-09-03, the `image` job) was the first hang with the probe's in-process watchdog armed. It printed `work complete, exiting 0`, then `process 'exit' event reached, code 0`, then **nothing** for five minutes — no handle dump, no warning. That is a state the probe's own diagnostic table did not list: the JS exit handlers ran, and the process stuck in the native teardown that follows them, where libvips and glib take down their thread pools. A JS timer cannot fire there, because the event loop is already gone. The watchdog was placed in the one process that cannot see the fault. The environment line was identical to every passing run's, so it is not a difference between runners, and PR #64's render-parity run on the same day shows Node 26.8.1 and 24.20.0 rasterising the probes to the same bytes.
- **The guard moved outside the process.** `scripts/render-parity-probe.mjs` now runs itself as a child under a supervisor that loads nothing native. The child prints `PROBE VERDICT: exit <n>` as its last act before `process.exit(n)`; if it is still alive a grace period later, the supervisor kills it and exits `<n>`. Stdout is unchanged apart from that one line, so `tee`, the Report step and the `--strict-fonts` gate read what they always read. Each rescue prints an Actions `::warning::` naming OA-052, so the frequency stays countable: a green run carrying that warning is a hang that was outlived.
- **It is not muting a check, and that is proven rather than asserted.** `scripts/test-render-parity-supervisor.mjs` runs the real rasterisation four times: a clean run exits with its verdict; a forced non-zero verdict passes through as itself; a thread blocked in the exit handler — the eighth hang's exact shape, where the in-process watchdog provably cannot fire — is rescued in seconds with the verdict's own code; and a thread blocked *before* the verdict is waited out, not rescued. A mutant that armed the rescue on any line instead of the verdict line turned the fourth case red before this landed. A hang in the work still ends in the step's five-minute cap, exactly as before, and would be new: no hung run has ever shown one.
- **What is still not known is which native destructor blocks**, and this change does not need to know. The probe header records the eighth log, the supervisor's reasoning and the test seams; the workflow header's paragraph about `cancelled` versus `failure` is corrected in place.
