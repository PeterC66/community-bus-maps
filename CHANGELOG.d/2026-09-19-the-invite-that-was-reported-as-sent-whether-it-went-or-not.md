date: 2026-09-19
title: "The admin console said “The invite has been emailed” whether or not one had been, and the delivery counters it could have checked were on no screen"
---

- **`POST /api/admin/applications/:id/approve` now returns `emailed` and `emailError`, and the banner branches on them.** It computed `r.sent`, wrote it to a server console nobody reads, and returned `ok: true` either way; the browser then branched on whether it had been handed a **dev link**, so in production — where `DEV_LINKS` is off — it printed *"The invite has been emailed"* unconditionally. A customer could be created, no email leave the building, and the operator be told one had, with the only record a line in the VPS process log (buses-data OA-362).

- **The same fault in the same words was fixed once already, one route away.** `src/email/health.js` exists because `sendMagicLink` reported success when a *configured* provider threw — bad key, outage, suspended domain — and its header comment describes that defect exactly. `POST /maps/:id/advisers`, built later, answers with `emailed` and `emailError`. The approve route is the older one and kept the shape the audit condemned; `POST /admin/users` — the route that adds a customer's **second** user — kept it too, so the sentence fired twice on the first real customer. Both now answer the same way.

- **Three outcomes on the screen, not two, and the link is shown in the one that needs it.** Emailed; not emailed, *here is the link to send by hand*; and failed with the error named. A grant or an account without a link reaches nobody, so the route hands the link back whenever nothing was sent — `DEV_LINKS || !emailed` — rather than only in development.

- **A warning can now stay on screen.** `banner()` recognised exactly one sticky kind, `ok-sticky`, so the only notice that could persist was a success one — and a warning carrying a sign-in link the operator has to copy is precisely the one that must not vanish after eight seconds. Any `<kind>-sticky` is sticky now, and the suffix is stripped before the class is set.

- **The Ops tab renders email delivery, which the server has computed since P7 and no screen showed.** `activity.email` — `lastSentAt`, `totalSent`, `totalFailed`, `consecutiveFailures`, `lastError` — has been in `/api/admin/ops` all along, and a grep of `public/` for any of those field names returned nothing: answering *did that invite actually go?* meant opening a raw JSON endpoint nothing links to, and knowing that the route sends before it writes its audit event. The Health chip beside it is `configStatus()` — a provider is **named** and a key is **present** — which reads as an assurance about delivery and is not one. The card says the counters are in memory and a deploy resets them, so a zero cannot be misread as *nothing has ever failed*.

- **The audit row carries the send outcome**, because the counters are a fact about the process and `emailed` is a fact about that request — the first survives no restart.

- **Both new arms are exercised for real and the control fakes only the network.** With no provider configured, and with an unknown one that makes `sendEmail()` throw by its own declared contract, `scripts/test-approve-application.mjs` asserts the approval still succeeds, that the answer says nothing was sent, that the throwing arm names why, and that the link comes back. Every arm reachable without a network answers `emailed: false`, so a route hard-coding it would pass all of those — the control therefore replaces `globalThis.fetch`, the outermost boundary there is, leaving the whole real path from `sendMagicLink` through `sendViaResend` to `recordSendSuccess` intact, and requires `emailed: true`. Hard-coding `emailed` reddens that control; dropping `emailError` reddens three other assertions. Both were watched.
