date: 2026-09-14
title: "Deleting a map with a local adviser"
---

- **Deleting a map that had a local adviser threw a foreign-key error and deleted nothing.** `scripts/delete-map.mjs` clears the tables a map owns from a list typed in August; `map_adviser_grant` arrived three weeks later for the adviser's seat with `map_id INTEGER NOT NULL REFERENCES map(id)`, and `PRAGMA foreign_keys = ON` has been set throughout. The whole delete is wrapped in `BEGIN`/`COMMIT`, so nothing was ever corrupted — it rolled back and reported a bare SQLite constraint error instead of anything about advisers. The script now clears the grants, and revoking is not an alternative: a revoked grant keeps its row, which is the point of `revoked_at`, so the constraint bites just the same.

- **It names every adviser it is about to drop, before the `--yes` gate and again after the delete.** A grant is one person's standing invitation to look at one map, arranged by a human in writing, and the town still has a map after a re-import. The advisers also go into the `map.delete` audit detail as `{ userId, email, note }` — the same shape `adviser.grant` and `adviser.revoke` already use, so one query over the append-only log answers *who could see this map* across all three. A revoked grant is counted but not listed: it names somebody with no access left to lose.

- **The test's population is the schema, not a list.** `npm run test:delete-map` parses `src/db/schema.sql` for every column declaring `REFERENCES map(id)` and requires the script to clear that table, so the next table to reference a map fails on the day it is written rather than the day somebody deletes a map. It also pins the two tables that carry a `map_id` with **no** foreign key — `message` and `audit_log` — because their rows outliving the map is deliberate, and a later tidy-up adding a constraint would break the delete. Then it does it for real against a throwaway database: a map with a live grant, a revoked grant, a version, a publish request and a feedback message, with every consequence asserted.

- **The falsification arm is the real bug, not an invented one.** `npm run test:prove-red-delete-map` arm 1 fetches `scripts/delete-map.mjs` as it stood on `main` before this change and requires the test to refuse — both halves, the static check and the actual delete. If the fix ever lands on the base the arm reads, the harness says so and fails rather than going quietly green. Five more arms cover a removed clear line, a new table referencing `map(id)` (which is what proves the population is derived), a foreign key added to `message.map_id`, a delete against the audit log, and the dry run losing its adviser listing. 90 tests, 0 failed.

- **`docs/R1-create-map.md` now describes two paths and says which is which.** *Wrong customer* — the owner was recorded wrongly and the map is otherwise theirs — is a repair, keeps the map id, slug and version series, and uses the owner picker. **A real customer taking over one of our samples is a different job**: delete the sample row and re-import it owned by them, which is what `delete-map.mjs` was written for and says so in its own header. Peter's decision, 2026-09-14, and the deciding reason is the version number — a sample we have rebuilt eight times reads "Version 8.0" on the sheet and on its public page, because `major` counts accepted data refreshes; a fresh import renders v1.0 and, because the importer passes `sample: isSampleCustomer(<the new owner>)`, comes out without the pilot band from the first byte rather than being re-stamped afterwards. Renumbering in place is not available at all: `UNIQUE (map_id, major, minor)`, and every map already owns a v1.0.
