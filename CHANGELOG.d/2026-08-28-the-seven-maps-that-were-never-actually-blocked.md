title: "Correction: the seven maps were never actually blocked — the fault was in the measurement"
---

- **The entry immediately before this one is wrong in its headline claim, and this corrects it.** It said seven of the eighteen live maps could not be re-rendered and so could receive no update. **They could all be re-rendered, and always could.** Measured on the live host on 2026-08-27, *after* deploying the engine fix but *before* `track-engine.mjs --apply` — so every pack was still running the generator it was imported with, the one that invents the river — the sweep reported **18 maps swept, 0 cannot be re-rendered**, and the portal's own `previewFrom(mapDataDir(id), {}, {})` rendered all seven of the named maps, internal and external.
- **What the original measurement did was invoke each map's generator without composing `base-overrides.json` into `OVERRIDES_FILE`.** Every render path in `src/maps/engine.js` does compose it — `previewFrom`, `renderVersion`, `enumeratePoisFromDir`, and `src/expert/index.js` — because `import-map.mjs` deliberately stores a shipped `overrides.json` under that name. Leave the composition out and exactly those seven refuse, with exactly the reported message, and with the extra `panel:` lines on exactly the two maps named. The measurement was describing its own harness.
- **The local reproduction agreed for the same reason, which is the part worth remembering.** The sweep written to confirm the finding has a `--drop-framing` mode that models precisely the composition the first measurement omitted. It reproduced all seven, including which two maps carried extra detail, and the match was read as confirmation. Two harnesses built on one assumption are one experiment, not two — and neither had asked the product. What settled it was calling the function an accepted update actually runs.
- **The engine change itself stands and stays.** `gen_internal.js` invents no feature when there is neither a `features[]` nor any river geometry; `build_internal_place.js`'s `suppressOrphanRiver` is gone. That removed a real fragility — the framing had to survive delivery, import, engine tracking and the customer merge, four systems each having to remember to carry a side file, which nobody can verify by reading any one of them. On the live host after the fix, `--drop-framing` reports **0 of 18 refusing** where it reported 7. The dependency was real; what was never true is that it had already broken.
- **`track-engine.mjs --apply` was run on the live store**: 38 packs current, 0 behind. Stored sheets untouched, as that script promises — what changes is the next render of each map. Health checks all ok, 18 maps, live at `0.10.0-pilot+d57de25`.
- **One real bug came out of it.** `render_sweep.js` pushed a `NO-GEN` row without the `refusals`/`refused` fields every other row carries, and the summary threw `Cannot read properties of undefined` the first time a run had both a refusing map and a missing generator — a combination that cannot occur on the laptop, where every generator is present, so it first appeared on the live host mid-measurement. Fixed, and reproduced deliberately to prove the fix.
